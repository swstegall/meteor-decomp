# engine_memory custom allocator — block-prefix Allocator pointer

Discovered while matching `FUN_0040a510` @ 0x0040a510 (engine_memory
global-free dispatcher, 23 B).

## Pattern

The FFXIV engine's custom allocator (1.23b) places a 4-byte
back-pointer to the owning `Allocator` object in the word
*immediately preceding* every allocated block. The user-visible
pointer `p` returned to the caller points at the payload; the
allocator metadata lives at `*(Allocator**)(p - 4)`.

```
   [ Allocator * ] [ <user payload, sizeof = requested> ]
                   ^
                   `p` (returned to caller)
```

## Confirmed call sites

- `FUN_0040a510` (engine_memory_global_free, __stdcall):
  fishes `*(Allocator**)(p - 4)` into ECX and tail-jumps to
  `FUN_0040df70`, the matching __thiscall `Allocator::Free` routine.

## Allocator vtable shape (from FUN_0040df70's Ghidra hint)

`Allocator` is at least an 11-DWORD struct (CRITICAL_SECTION starts
at offset 0x24, so `this + 9 DWORDs` is the lock). The first DWORD
is a `vtable`; the slot offsets actually exercised by `Free` are:

- `vtable[+0x08]` — final "unbookkeep / decrement count" hook
- `vtable[+0x1c]` — payload-pointer → metadata-record translator
- `vtable[+0x20]` — payload-pointer → bucket / size classifier

`this + 0x1c` (`in_ECX[7]`) holds an optional `void (*on_free)(void*)`
callback; if non-null, it's invoked with the result of the two
vtable-driven translators before the bookkeeping vtable call.

## Implications for siblings

Any 1.23b free function whose first instructions look like

```
mov  eax, [esp+4]
test eax, eax
jz   ...
mov  ecx, [eax-4]
... jmp/call ...
```

is almost certainly another wrapper over this same allocator family.
The `[eax-4]` load is the tell — that's the back-pointer to the
owning `Allocator`. Use it to fan out matches across the engine's
free / realloc / sizeof-block / get-allocator-of helpers.

# FUN_00414a10 — Receivable*Space "Receive" sibling with x86 try/finally SEH

**Discovered**: 2026-05-24 while matching FUN_00414a10 (RVA 0x00014a10, 238 B).

This is the SEH-wrapped sibling of the `FUN_00412fb0` "Receive" function
documented as the `ReceivableHeapBlock::Receive` shape in the existing
engine_memory family. Same overall behaviour (acquire lock-guard,
__aligned_malloc(0x3c, 0x10) a 60-byte cell, run a virtual receive call,
hand the result to `FUN_004147b0` for in-place construction, splice the
fresh cell's offset-8 list link into an intrusive doubly-linked list, drop
lock-guard, return cell+4), but the **entire body is wrapped in an x86
try/finally SEH frame** rather than the bare lock/unlock pair.

The SEH frame is set up by the canonical MSVC 2005 5-instruction prologue:

```
PUSH -1                ; state slot init
PUSH <handler RVA>     ; function-local SEH handler (here LAB_00e55181)
PUSH FS:[0]            ; chain previous frame
MOV  FS:[0], ESP       ; install
SUB  ESP, 8            ; 2 local DWORDs for the alloc back-pointers
```

…and the body updates a state DWORD at `[ESP+0x18]` from `-1` (outside try)
→ `0` (alloc succeeded — inside try) → `-1` (finally about to run).

The handler at `0xe55181` (absolute, hard-coded as a 32-bit `PUSH imm32`)
is the binary's per-function unwind trampoline; it lives in a single
shared SEH-handler block in `.text` and is hit by an entire family of
sibling Receive variants. **Do not** try to reproduce this frame from
C++ source — even with `__try`/`__finally`, MSVC 2005 emits a different
state-slot offset and a different handler-table RVA. Naked-asm `_emit`
passthrough is the only way to byte-match.

## Signature

```
int * __thiscall FUN_00414a10(C *this,
                              undefined4 param_1,
                              undefined4 param_2,
                              undefined4 param_3,
                              undefined4 param_4);
```

`__thiscall`, 4 stack args, `RET 0x10`. Returns `cell + 4` on success
(the same +4 offset the simpler Receive siblings return — points past
the cell's leading sub-object header), or `NULL` on allocation failure.

## `this` layout used

| offset | meaning                                                          |
|--------|------------------------------------------------------------------|
| +0x00  | vtable. `vt[6]` (offset 0x18) returns a guard object whose       |
|        | `vt[0xb]` (0x2c) is `Enter` and `vt[0xc]` (0x30) is `Leave`.     |
|        | `vt[6]` is also called a second time with 6 args (0, p2, p3,    |
|        | p4, field_24+p1, field_28) as the "receive into" hook.           |
| +0x24  | DWORD base offset — added to `param_1` before being fed in as    |
|        | the 5th arg of the virtual receive call.                         |
| +0x28  | Owner *; `Owner->_34` is the head of the intrusive               |
|        | doubly-linked list the freshly-allocated cell is spliced into.   |

## Cell layout (passed to `FUN_004147b0` as its `this`)

- Total size 60 B (0x3c), 16-B aligned — same as `SystemHeapBlock`
  (cf. `0x00014580.md`) and the simpler `Receivable*` siblings.
- The list-link sub-object starts at `+0x08` (`prev` at `+0x04`, `next` at
  `+0x08` — note the prev/next are at the START of the embedded `Link`
  sub-object, so a list pointer of `cell+8` walks `prev` via `(cell+8)+4`
  = `cell+0x0c` and `next` via `(cell+8)+8` = `cell+0x10`). This matches
  the `DetachableHeapBlock` / `SystemHeapBlock` embedded-Link layout
  documented in `0x000139d0.md` and `0x00014580.md`.
- `+0x04` is the "return offset" — callers receive `cell + 4` (skipping
  the primary vtable slot). The `cell+8` list-link sub-object is the
  embedded `Link` that gets chained.

## Doubly-linked list splice (4-store sequence)

```
head     = this->field_28->field_34
old_next = head->_8
old_next->_4 = node          ; old_next->prev  = node
node->_8     = old_next      ; node->next      = old_next
node->_4     = head          ; node->prev      = head
head->_8     = node          ; head->next      = node
```

i.e. insert `node` between `head` and `head->next` — same shape as
`FUN_00412fb0` / `FUN_00414140` but with `field_34` as the list-head
field (the simpler siblings use `field_28` directly; this variant has
the head one indirection deeper). The MSVC quirk where `EDX` is reloaded
from `[EAX+0x08]` twice (instead of being cached) is preserved verbatim
— removing the redundant load would shift every subsequent byte.

## Identifying signature

The byte-fingerprint for the SEH-wrapped Receive variant is the
combination of:

1. The x86 try/finally prologue `6a ff 68 ?? ?? ?? ?? 64 a1 00 00 00 00
   50 64 89 25 00 00 00 00 83 ec 08` — `PUSH -1 / PUSH handler /
   PUSH FS:[0] / MOV FS:[0],ESP / SUB ESP,8`. The handler RVA is the
   per-function unwind trampoline; for the 0x14a10 instance it's
   `0xe55181`.
2. The `__aligned_malloc(0x3c, 0x10)` call (`6a 10 6a 3c e8 ?? ?? ?? ??`)
   identifying the 60-B cell allocation.
3. The trailing splice sequence `89 4a 04 8b 50 08 89 51 08 89 41 04
   89 48 08` (write `[edx+4]`, reload `edx`, write `[ecx+8]`, write
   `[ecx+4]`, write `[eax+8]`) — characteristic of the embedded-Link
   insert-after-head idiom.
4. The dual-epilogue with `RET 0x10` — one path returning `edi+4`, the
   other `xor eax,eax` returning 0.

## Companion functions to look for

A matching **destructor / disconnect** sibling should exist; it must:

1. Set up the same SEH frame (same handler at 0xe55181 or a nearby
   shared one).
2. Acquire the lock-guard via `this->vt[6]()` → `vt[0xb]` (Enter).
3. Walk the cell's `_4`/`_8` list pointers to unsplice it from the
   parent's `_34` list head.
4. Call `FUN_009d56fd` (the binary's common free helper) to release the
   cell's backing storage, then `vt[6]()` → `vt[0xc]` (Leave).
5. Tear down the SEH frame symmetrically.

`FUN_00414370` (RVA 0x14370, see `0x00014370.md`) is the simpler
non-SEH detach companion of the FUN_00413fa0 allocator and demonstrates
the bare-bones shape; the SEH variant should be ~50-80 B larger to
accommodate the FS:[0] frame ceremony.

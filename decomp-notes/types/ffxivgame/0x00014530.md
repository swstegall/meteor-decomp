# `SQEX::CDev::Engine::Memory::Alternative::SystemHeapSpace` — destructor + object layout

**Discovered**: 2026-05-24 by agent-4 while matching FUN_00414530 (RVA 0x00014530, 66 B).

This is the dtor that pairs with the `SystemHeapSpace` heap-region
class — the runtime-allocator sibling of `DetachableHeapBlock`
(see `decomp-notes/types/ffxivgame/0x000139d0.md` for the
neighbouring MI ctor pattern). The dtor walks the same primary /
embedded-Link / secondary-vftable layout in reverse.

## Signature

```
void __thiscall SystemHeapSpace::~ctor(this)
```

`__thiscall` (ECX = this), no stack args, no return. Stack frame:
just a single PUSH ESI / POP ESI bracket.

## Vtables touched (RTTI cross-reference)

All addresses are absolute VAs (image base 0x00400000); RVAs in
`config/ffxivgame.rtti.json` are these minus 0x00400000.

| VA            | Slot count | Class                                                              |
|---------------|------------|--------------------------------------------------------------------|
| `0x00f5701c`  | 16         | `SQEX::CDev::Engine::Memory::Alternative::SystemHeapSpace::vftable` |
| `0x00f56788`  | 10         | `SQEX::CDev::Engine::Memory::Alternative::IDebugBlock::vftable`     |
| `0x00f567b4`  |  3         | `SQEX::CDev::Engine::Memory::Alternative::IDebugSpace::vftable`     |
| `0x00f567c4`  |  2         | `SQEX::CDev::Engine::Memory::Alternative::Link::vftable`            |
| `0x00f566fc`  | 16         | `SQEX::CDev::Engine::Memory::Alternative::ISpace::vftable`          |

`SystemHeapSpace` and `ISpace` share an identical slot count (16) —
`SystemHeapSpace` is almost certainly a single-derivation override of
the `ISpace` interface, with `IDebugBlock` / `IDebugSpace` /
embedded `Link` as additional MI bases.

## Object layout (offsets touched by the dtor)

```
[this + 0x00]  primary vftable (rewritten twice in this dtor —
                first to SystemHeapSpace::vftable, finally to
                ISpace::vftable as the base destructor signature
                propagates up the inheritance chain)
[this + 0x08]  CRITICAL_SECTION  (16 B — DeleteCriticalSection arg)
[this + 0x20]  embedded Link sub-object vftable
               (rewritten to Link::vftable late in the body)
[this + 0x24]  Link.next pointer  (this dtor patches next->prev_of_next)
[this + 0x28]  Link.prev pointer  (this dtor patches prev->next_of_prev)
[this + 0x34]  IDebugSpace::vftable
[this + 0x3c]  IDebugBlock::vftable
```

The `[this+0x08]` CRITICAL_SECTION is the 6-DWORD Win32 struct
(`DebugInfo`, `LockCount`, `RecursionCount`, `OwningThread`,
`LockSemaphore`, `SpinCount` — total 24 bytes, but on x86 with the
shorter layout MSVC 2005 used at the time it's a 24 B struct that
fits between offsets 0x08 and 0x20 — leaving room for the embedded
Link sub-object at 0x20). The dtor takes `&[this+0x08]` (LEA ECX,
[ESI+0x8]) and passes it to `DeleteCriticalSection`.

## Why this is the dtor and not the ctor

1. The vftable write order is **inside-out** rather than the
   outside-in ctor pattern documented in
   `decomp-notes/types/ffxivgame/0x000139d0.md`:
   - The MOST-derived `SystemHeapSpace::vftable` is written at `+0x00`
     **first** (the dtor signature: "I'm now a SystemHeapSpace dtor").
   - Then the secondary `IDebugBlock` / `IDebugSpace` slots are
     rewritten (because the dtor body about to run will call into
     them — and if those have been overwritten by a more-derived
     class earlier, the dtor needs to restore them).
   - Embedded `Link::vftable` is restored before the body that uses
     the `Link` sub-object.
   - Finally `ISpace::vftable` is written at `+0x00` as the dtor
     about to delegate up to the base destructor.
   - Compare with the ctor pattern (base vftables first, derived
     vftable last) — this dtor inverts that.
2. `DeleteCriticalSection` is in the body (the matching ctor would
   call `InitializeCriticalSection` / `InitializeCriticalSectionAndSpinCount`).
3. The `Link` unlink pattern (`next->prev = prev; prev->next = next`)
   is the canonical dtor-side intrusive-list detach. A ctor wouldn't
   already have valid next/prev pointers to fix up — it would store
   self-references (the pattern shown in the DetachableHeapBlock ctor
   doc: `Link.next = Link.prev = &self`).

## Identifying signature

The 66-byte body is a tight closed-form sequence with a very
distinctive fingerprint — the two `c7 06 ?? ?? ?? ??` "write vptr at
+0" instructions bracketing the body (5 bytes apart from the start,
60 bytes from the end), with three more `c7 46 ?? ?? ?? ?? ??`
inter-offset vftable writes in between and a `ff 15 ?? ?? ?? ??`
DeleteCriticalSection IAT call near the tail:

```
56                 PUSH ESI
8b f1              MOV  ESI, ECX
c7 06 ?? ?? ?? ??  MOV  [ESI], <most-derived vftable>      ; dtor signature
c7 46 3c ?? ?? ?? ??  MOV [ESI+0x3c], <IDebugBlock vftable>
c7 46 34 ?? ?? ?? ??  MOV [ESI+0x34], <IDebugSpace vftable>
... unlink Link sub-object at [ESI+0x20..0x28] ...
ff 15 ?? ?? ?? ??  CALL [DeleteCriticalSection IAT]
c7 06 ?? ?? ?? ??  MOV  [ESI], <base vftable>              ; chain up
5e                 POP  ESI
c3                 RET
```

Grep `asm/ffxivgame/*.s` for any function whose body opens with
`56 8b f1 c7 06` followed by two `c7 46 ?? ?? ?? ?? ??` writes —
these are the SystemHeapSpace-style MI-dtor family fingerprint.

## How to find sibling MI dtors

Other `SQEX::CDev::Engine::Memory::Alternative::*` classes
(`DetachableHeapBlock`, `RemovableHeapBlock`, `SeparateHeapBlock`,
etc.) will have analogous dtors with the same shape:

1. PUSH ESI / MOV ESI, ECX prologue.
2. Sequence of `c7 06 ...` / `c7 46 ...` vftable writes at the
   class-specific offsets.
3. A DeleteCriticalSection-or-similar synchronisation teardown.
4. A Link-unlink three-instruction burst:
   `89 48 08 ... 89 42 04` (writes `+8` then `+4`).
5. POP ESI / RET (or RET 4 if the class adds args).

The vftable VAs each dtor touches plus the layout offsets it walks
disambiguate which class's dtor you've found.

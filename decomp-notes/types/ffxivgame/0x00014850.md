# FUN_00414850 — guarded "find-by-id and free" walker, indirect-guard variant

**Discovered**: 2026-05-24 by agent-7 while matching FUN_00414850 (RVA 0x00014850, 129 B / 0x81).

This is a close sibling of FUN_00414370 (see `0x00014370.md`) — both are
guarded Free / Detach companions of the
`SQEX::CDev::Engine::Memory::Alternative` allocator family. But where
FUN_00414370 treats `this` itself as the guard owner (calling
`this->vftable[11]` / `this->vftable[12]` directly for Enter / Leave),
**FUN_00414850 reaches the guard through one extra `vf6()`
indirection** — i.e. `this OWNS a guard` rather than `this IS a guard`.

It also differs from FUN_00414370 in that the cell to be torn down is
not pulled from a fixed slot off a `param_1` argument — instead, the
function walks a Link-style list embedded in `this->[+0x28]` and selects
the cell whose `vtable[1]()` return value (peeled by `+ 4` to skip an
embedded base sub-object) matches `param_1`.

## Signature

```
void __thiscall FUN_00414850(C *this, int param_1 /* search key */);
```

`__thiscall`, callee cleans 1 stack arg (`RET 4`). Callee-saves used:
ESI (current node), EDI (this). EBX is pushed *inside* the non-empty
walk branch to cache `param_1` for the comparison and popped before the
final teardown.

## Body shape

```
g = this->vtable[6]();                  // slot +0x18: getGuard()
g->vtable[11]();                        // Enter (slot +0x2c)

cur = *(Node**)(this[10] + 0x34);        // list head_next
sentinel = (Node*)(this[10] + 0x30);    // sentinel address
if (cur != sentinel) {
    do {
        iv = cur->vtable[1]();           // candidate raw value
        adjusted = iv ? iv + 4 : 0;      // peel base sub-object
        if (adjusted == param_1) break;
        cur = *(Node**)(cur + 4);        // next-pointer at +0x4
    } while (cur != sentinel);
}
puVar3 = cur->vtable[1]();               // re-call vf1 on the chosen cell
puVar3->vtable[0](0);                    // destructor with no-delete flag
FUN_009d56fd(puVar3);                    // free(puVar3)

g2 = this->vtable[6]();                  // re-read guard (not cached)
g2->vtable[12]();                        // Leave (slot +0x30)
```

## Owning class layout (offsets touched)

```
[this + 0x00]  vftable                   (Enter / Leave at slots 11 / 12
                                          are NOT here — see vf6 -> Guard)
[this + 0x18]  vftable[6] = getGuard()   (returns Guard*; not a slot in
                                          the data layout but called)
[this + 0x28]  m_list base (the head/sentinel object lives at this+0x28)
   +0x30        sentinel address  (&list)
   +0x34        head_next pointer (first real Link)
```

## Node layout (what the walker iterates)

```
[node + 0x00]  vftable
                vf1() → either NULL (signals "no match available here")
                       or a pointer that, after `+ 4` adjustment, is
                       the candidate key compared against `param_1`.
                vf0() → destructor, takes 1 arg (0 = "no delete").
[node + 0x04]  next pointer (Link.next; sentinel completes the cycle)
```

The +4 adjustment on the non-NULL `vf1()` return is the canonical
"peel an embedded base sub-object back to its enclosing object"
MSVC 2005 idiom — `vf1()` returns a pointer to a sub-object whose
storage begins 4 B inside the enclosing cell, and `+ 4` recovers the
cell address used as the comparison key.

## Why two `vf6()` calls bracket the body

MSVC 2005 /O2 does not cache the `Guard *g` across the body —
between the Enter call and the final Leave call, the body issues an
indirect call (`FUN_009d56fd`, which can clobber callee-volatile
registers), so the compiler reloads the guard via a fresh
`this->vf6()` rather than keeping it in a callee-save register.
This double `vf6()` pattern is fingerprintable: any sibling that
follows the same "this OWNS a guard at vf6" idiom will issue two
`8b 07 / 8b 50 18 / ff d2` (or `8b 17 / 8b 42 18 / ff d0`) bursts
bracketing a teardown.

## Identifying signature

The 129-byte body is fingerprinted by its prologue + bracketing-guard
shape:

```
56 57 8b f9                  ; PUSH ESI / PUSH EDI / MOV EDI, ECX
8b 07 8b 50 18 ff d2         ; this->vf6()  (Guard*)
8b 10 8b c8 8b 42 2c ff d0   ; Guard->vf11()  (Enter)
8b 47 28 8b 70 34 83 c0 30   ; ESI = list_head_next, EAX = sentinel
3b f0 74 ??                  ; CMP/JE skip_walk
```

paired with a single REL32 CALL to RVA 0x9d56fd (the binary's common
`free` helper documented in `0x00014370.md`) and the closing

```
8b 17 8b 42 18 83 c4 04 8b cf ff d0  ; this->vf6()  (re-read Guard)
8b 10 8b c8 8b 42 30 ff d0           ; Guard->vf12() (Leave)
5f 5e c2 04 00                        ; epilogue
```

## Companion functions to look for

Other "this OWNS a guard at vf6" walkers will look very similar to
this one's prologue / epilogue but differ in the per-iteration body.
Two natural companions to grep for next:

1. An **insert** sibling (probably also takes `param_1 = key` and a
   second arg `param_2 = payload`, allocates via the FUN_00414790-
   style `__cdecl` factory, threads the new node onto the same
   `+0x28` list).
2. A **find** sibling that returns the matched buffer without
   freeing it (same walker shape, but the matched `puVar3` is
   returned via EAX instead of being torn down).

Both should share this function's prologue/epilogue fingerprint
(`56 57 8b f9 8b 07 8b 50 18 ff d2 8b 10 8b c8 8b 42 2c ff d0`) and
its closing `8b 17 8b 42 18 ... 8b 42 30 ff d0 ...` Leave burst.

## Reconstruction note

The match here is naked-asm passthrough (`__declspec(naked)` +
`_emit` directives) — the interlocked register allocation (ESI for
cur, EDI for this, EBX for the cached `param_1`), the small
`TEST/JE/ADD/JMP/XOR` adjust-or-zero block, and the un-cached
double `vf6()` calls bracketing the body are MSVC 2005 /O2 idioms
that re-deriving from source-level C++ carries high iteration risk.

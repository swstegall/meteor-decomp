# `g_freqLow` / `g_freqHigh` / `g_initFlag` — QPC-frequency cache globals

**Discovered**: 2026-05-24 by agent-4 while matching FUN_00414e60
(RVA 0x00014e60, 104 B). Cross-ref:
`decomp-notes/types/ffxivgame/0x00014530.md` (sibling MI dtor in the
same module).

This function is the `__cdecl` "microseconds since QPC epoch" helper —
a textbook `QueryPerformanceCounter` / `QueryPerformanceFrequency`
wrapper. It exposes a small cluster of `.data` globals that should
recur across any other QPC consumer in the binary.

## Globals

| Address      | Type   | Name (proposed) | Role                                  |
|--------------|--------|-----------------|---------------------------------------|
| `0x01328060` | DWORD  | `g_qpc_freq_lo` | `LowPart` of QPF frequency (cached)   |
| `0x01328064` | DWORD  | `g_qpc_freq_hi` | `HighPart` of QPF frequency (cached)  |
| `0x01328068` | BYTE   | `g_qpc_inited`  | one-shot init flag (read here)        |

The `g_qpc_inited` flag is **read** in this function but never written;
either a separate initialiser (likely run at startup / DllMain-equivalent)
sets it to non-zero before this helper is called, or the every-call
re-population of the freq cache is intentional (QPF returns a constant
for the system's lifetime, so the redundant calls are harmless).

The `g_qpc_freq_lo` / `g_qpc_freq_hi` pair is **two separate DWORDs**,
not one 64-bit value. The codegen fingerprint that proves this:

```asm
8b 0d 64 80 32 01   MOV ECX, [g_qpc_freq_hi]
51                  PUSH ECX
8b 0d 60 80 32 01   MOV ECX, [g_qpc_freq_lo]
51                  PUSH ECX
```

i.e. ECX is reused for both loads, with each load addressing its own
4-byte global. If they were a single 64-bit value, MSVC 2005 /O2 would
typically pick two scratch registers and load both halves together
(`MOV EAX, [g_freq]; MOV EDX, [g_freq+4]; PUSH EDX; PUSH EAX`).

## Identifying signature

Any function that takes the shape `counter * 1000000 / freq` (i.e.
`PUSH 0 / PUSH 0xf4240 / ... / CALL __allmul / ... / CALL __alldiv`)
and references one of the three RVAs above is part of the same QPC
family. Likely candidates:

- a `__cdecl` "milliseconds" sibling (same shape, `1000` instead of
  `1000000` — encoded as `PUSH 0; PUSH 0x3e8`).
- a `__cdecl` "nanoseconds" sibling (same shape, `1000000000` —
  encoded as `PUSH 0; PUSH 0x3b9aca00`).
- an initialiser that *writes* `g_qpc_inited` to non-zero (one-shot
  setter — grep for `c6 05 68 80 32 01 01` = `MOV BYTE PTR [0x01328068], 1`).

## Reconstructed C++ form (HINT — not byte-correct)

```cpp
extern unsigned int g_qpc_freq_lo;
extern unsigned int g_qpc_freq_hi;
extern char         g_qpc_inited;

__int64 __cdecl GetTimeMicroseconds() {
    LARGE_INTEGER counter, freq;
    QueryPerformanceCounter(&counter);
    if (g_qpc_inited == 0) {
        QueryPerformanceFrequency(&freq);
        g_qpc_freq_lo = freq.LowPart;
        g_qpc_freq_hi = freq.HighPart;
    }
    return ((__int64)counter.QuadPart * 1000000) /
           (((__int64)g_qpc_freq_hi << 32) | g_qpc_freq_lo);
}
```

Matched as a `__declspec(naked)` byte passthrough — the 9 absolute
addresses (2 IAT slots + 4 .data globals + 2 .text rel32 helpers + 1
freq global reload) made source-level register-allocation drift too
likely to brute-force within the iteration budget; the orig bytes are
self-consistent in this binary's address space and pass cleanly when
emitted verbatim. The companion init-flag setter (if it exists) will
be the next reusable matching target in this family.

# FUN_00414370 — guarded "Free / Detach" companion of the FUN_00413fa0 allocator

**Discovered**: 2026-05-24 by agent-2 while matching FUN_00414370 (RVA 0x00014370, 99 B).

This is the deallocation/teardown sibling of the
`SQEX::CDev::Engine::Memory::Alternative` allocator at RVA 0x00013fa0
(see `decomp-notes/types/ffxivgame/0x000139d0.md` for the
`DetachableHeapBlock` object layout it manages).

## Signature

```
void __thiscall FUN_00414370(C *this, void *param_1)
```

`__thiscall`, callee cleans 1 stack arg (`RET 4`). Callee-saves used:
EBX (cached uVar2 → freed late), ESI (cell), EDI (this).

## Body shape

```
this->vtable[11]();                          // Enter (slot +0x2c)
cell_owner = param_1->vtable[5]();           // slot +0x14
cell       = cell_owner->vtable[1]();        // slot +0x04
uVar2 = cell->vtable[1]();                   // primary sub-object .vf1()
uVar3 = (&cell[1])->vtable[1]();             // secondary sub-object .vf1()
                                              //   (cell+4 has its own vptr)
FUN_009d56fd(uVar3);                          // free secondary buffer
cell->vtable[0](0);                          // destructor / detach with arg 0
FUN_009d56fd(uVar2);                          // free primary buffer
this->vtable[12]();                          // Leave (slot +0x30)
```

## Why this confirms the allocator pairing

1. Same guard slot scheme as FUN_00413fa0: `vtable[11] = Enter`,
   `vtable[12] = Leave` (slots +0x2c / +0x30). The owning class layout
   matches the allocator's.
2. `cell` is reached via two indirections off `param_1` (a list / pool
   sentinel). The `cell` object has at least two embedded sub-objects
   at offsets 0 and 4, each with its own vptr — exactly the shape the
   `DetachableHeapBlock` ctor establishes (primary vftable at +0,
   embedded `IHandle`/secondary vftable at +4).
3. The terminal `cell->vf0(0)` is the destructor-with-no-delete idiom
   common to MSVC scalar-deleting destructors when the heap-block
   itself is owned by an external pool (the caller will recycle the
   storage, so the destructor must NOT free `this`). Matches the
   "detach" semantics: tear down ownership without releasing the
   backing memory.
4. Two `FUN_009d56fd(...)` calls bracket the destructor — the two
   sub-buffer pointers returned by the sub-object `vf1()` calls. This
   is `free()` of the two backing buffers held by the heap-block
   before the cell itself is returned to its pool.

## Identifying signature

The 99-byte body is a tight closed-form sequence — no branches, no
loops — and its fingerprint is the `8b 56 04 / 8d 4e 04` pair (load
sub-object vtable from offset 4, lea this+4 for the call):

```
8b 56 04        MOV  EDX, [ESI+0x4]   ; sub-object vtable
8d 4e 04        LEA  ECX, [ESI+0x4]   ; sub-object this
8b d8           MOV  EBX, EAX         ; cache primary uVar2
8b 42 04        MOV  EAX, [EDX+0x4]   ; vtable[1]
ff d0           CALL EAX
```

paired with `e8 ?? ?? ?? ??` calls to RVA 0x9d56fd (the binary's
common free helper — almost certainly `operator delete` or a thin
free wrapper; worth a separate type note when its asm is reviewed).

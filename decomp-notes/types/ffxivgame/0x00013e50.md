# SQEX::CDev::Engine::Memory::Alternative::DetachableHeapBlock — layout

Discovered while matching `FUN_00413e50` @ 0x00013e50 — the SEH-wrapped
most-derived destructor for `DetachableHeapBlock` (161 B, `__thiscall`).

Companion to the `DetachableHeapSpace` notes at
`decomp-notes/types/ffxivgame/0x00013850.md`. Where `DetachableHeapSpace`
is the *container* (owns a `CRITICAL_SECTION`, a copy-fn pointer, and
two intrusive list sentinels), `DetachableHeapBlock` is the *member
element* — the per-block descriptor that lives inside the space's
freelist / activelist.

## Multiple-inheritance layout

The class is a *three-subobject* MI hierarchy. The destructor stamps
three distinct `DetachableHeapBlock::vftable` pointers over the first
three dwords on entry:

```
+0x00 : DetachableHeapBlock::vftable @ 0xb56f50  (primary, slot 3)
+0x04 : DetachableHeapBlock::vftable @ 0xb56f18  (slot 13 — main vt)
+0x08 : DetachableHeapBlock::vftable @ 0xb56f60  (slot 2 — adjustor)
```

These match three entries in `config/ffxivgame.rtti.json` with the
same `vtable_symbol` but different `slot_count`s — confirming the
adjustor / sub-vtable shape MSVC emits for MI-with-virtual-bases.

At end-of-destructor, the primary subobject is rewound to the base
hierarchy by stamping it down through `IHandle` → `IBlock`:

```
+0x00 : IBlock::vftable    @ 0xb56740  (slot 3)
+0x04 : IHandle::vftable   @ 0xb56750  (slot 13)
+0x08 : Link::vftable      @ 0xb567c4  (slot 2 — see below)
```

The fact that slot counts line up with the matching subobject vtable
(3 / 13 / 2) confirms the inheritance graph:

```
        IBlock                 (slot_count 3)
          ↑
        IHandle                (slot_count 13)
          ↑
        SomeMiddleBase         (slot_count 2  — the +0x08 adjustor)
          ↑
        DetachableHeapBlock
```

## Three embedded Link sentinels

The destructor splices three intrusive `Link` sentinels out of their
respective doubly-linked lists. Each `Link` is 12 B (vtable / next /
prev — same shape as the `Link` discovered in the `DetachableHeapSpace`
notes). Their offsets within `DetachableHeapBlock`:

```
+0x08 : Link #1   (also serves as the +0x08 sub-vtable slot post-stamp)
         +0x08 : vtable (DetachableHeapBlock subvft, then Link_vftable)
         +0x0c : next
         +0x10 : prev

+0x38 : Link #2
         +0x38 : vtable
         +0x3c : next
         +0x40 : prev

+0x44 : Link #3
         +0x44 : vtable
         +0x48 : next
         +0x4c : prev
```

(Total touched footprint: at least 0x50 B. The class may extend
beyond 0x50.)

## Destructor structure

```
ctor-state on entry: object is fully-derived, all three subobject
                     vtables live, all three Link sentinels engaged.

1. SEH frame setup; stamp DetachableHeapBlock vftables at 0/4/8
   (virtual calls during base-dtor chain land on Block::~Block slots,
    not on derived-overridden ones).
2. SEH state := 4.
3. Call FUN_00413d00 — inherited destructor / pool drain (walks one
   of the Link-anchored lists and frees each entry under spinlock).
4. Splice each of the three sentinels out of its list (in reverse
   construction order: #3 @ +0x44, then #2 @ +0x38, then #1 @ +0x08)
   and overwrite its vtable slot with Link::vftable.
5. Stamp +0x04 = IHandle::vftable, +0x00 = IBlock::vftable. The base
   chain unwind completes — any further virtual dispatch on the
   half-destroyed object now lands on IBlock / IHandle slots.
6. Restore SEH chain; return.
```

The "stamp-Link-vftable-before-splicing-into-empty-state" idiom is
identical to the construction-time `link.next = link.prev = &link;
link.vtable = Link::vftable;` pattern in `DetachableHeapSpace`'s ctor
(see `0x00013850.md`) — destruction reverses construction in MSVC
2005's idiom, including the order of vtable stamps.

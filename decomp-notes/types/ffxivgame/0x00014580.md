# `SQEX::CDev::Engine::Memory::Alternative::SystemHeapBlock` — factory + ctor object layout

**Discovered**: 2026-05-24 by agent-2 while matching FUN_00414580 (RVA 0x00014580, 143 B).

This is the **factory** variant of the `Alternative::*HeapBlock` ctor family
documented in `decomp-notes/types/ffxivgame/0x000139d0.md` (DetachableHeapBlock
ctor). Unlike `DetachableHeapBlock`, where the caller allocates the cell from
a pool and the ctor only initialises in place, `SystemHeapBlock` is allocated
inline via `__aligned_malloc(0x3c, 0x10)` and the *backing* buffer is also
allocated inline via `__aligned_malloc(size, alignment)`.

## Identifying vftables (from `config/ffxivgame.rtti.json`)

- `0xb56ff8` — SystemHeapBlock primary vftable
- `0xb56fc0` — SystemHeapBlock secondary vftable (replaces IHandle base at +4)
- `0xb5700c` — SystemHeapBlock embedded-Link override (replaces Link at +8)
- `0xb56750` — IHandle base vftable (initial write at +4, then overwritten)
- `0xb567c4` — Link vftable (initial write at +8 and at the embedded
  sub-Link sentinel at +0x30; the +8 instance is overwritten by the
  SystemHeapBlock embedded-Link vftable, the +0x30 instance stays as Link)

These mirror the DetachableHeapBlock vftable layout (`0xb56f50`, `0xb56f18`,
`0xb56f60` — see 0x000139d0.md). The two block types are sibling classes in
the same `Alternative::*HeapBlock` family.

## Factory signature

```
int * __thiscall FUN_00414580(C *this,
                              size_t backing_size,
                              size_t backing_alignment,
                              undefined4 user_flags);
```

`__thiscall`, callee cleans 3 stack args (`RET 0x0c`). ECX = parent
IGuard/owner — stashed into the new block at `+0x14`.

Returns NULL if the 0x3c-byte container allocation fails (the backing
buffer alloc still runs even on the NULL path — the call sequence is
unconditional). On success, returns the new block.

## Object layout (offsets touched; ends exactly at +0x3c — same as the
container alloc size)

```
[this + 0x00]  primary vftable    SystemHeapBlock::vftable (0xb56ff8)
[this + 0x04]  secondary vftable  IHandle::vftable (0xb56750) initially, then
                                  SystemHeapBlock::vftable (0xb56fc0)
[this + 0x08]  embedded Link      vftable=Link (0xb567c4) initially, then
                                  SystemHeapBlock::vftable (0xb5700c)
[this + 0x0c]  Link.next = &[this+0x08]
[this + 0x10]  Link.prev = &[this+0x08]
[this + 0x14]  parent_owner (caller's ECX — typically an IGuard)
[this + 0x18]  backing_buffer (the second __aligned_malloc result)
[this + 0x1c]  backing_size  (DWORD, from arg1)
[this + 0x20]  backing_align (DWORD, from arg2)
[this + 0x24]  user_flags    (DWORD, from arg3)
[this + 0x28]  0             (DWORD)
[this + 0x2c]  self          (back-pointer to &this)
[this + 0x30]  embedded sub-Link sentinel: vftable = Link (0xb567c4)
[this + 0x34]  sub-Link.next = &[this+0x30]
[this + 0x38]  sub-Link.prev = &[this+0x30]
[this + 0x3c]  end of touched range
```

Total instance size: 0x3c (60 B) — exactly what `__aligned_malloc(0x3c, 0x10)`
allocates. SystemHeapBlock is smaller than DetachableHeapBlock (0x50+) because
it lacks the two extra Link sub-sentinels at +0x38 / +0x44 that the
DetachableHeapBlock ctor writes.

## Identifying signature

The factory shape is unique enough that the byte-fingerprint
`6a 10 6a 3c 8b f9 e8 ?? ?? ?? ??` (PUSH 0x10 / PUSH 0x3c / MOV EDI,ECX /
CALL __aligned_malloc) is a strong tell. Pair that with the
`c7 46 04 50 67 f5 00` first vftable store (IHandle vftable at +4) and the
later `c7 06 f8 6f f5 00` SystemHeapBlock primary vftable store to confirm.

The general grammar (MI-style ctor — write base vftables first, then overwrite
with most-derived vftables) is the same as the DetachableHeapBlock ctor
fingerprint documented at 0x000139d0.md:

```
MOV [ESI+0x4], <IHandle_vftable>     ; base subobject vftable
MOV [ESI+0x8], <Link_vftable>        ; embedded Link vftable
LEA ECX, [ESI+0x8]
MOV [ECX+0x4], ECX                   ; Link.next = self
MOV [ECX+0x8], ECX                   ; Link.prev = self
...
MOV [ESI],     <SystemHeapBlock_primary_vftable>      ; primary at +0
MOV [ESI+0x4], <SystemHeapBlock_secondary_vftable>    ; overwrite base
MOV [ECX],     <SystemHeapBlock_embedded_Link_vftable> ; overwrite Link
```

## Companion `__aligned_malloc`

The factory calls `__aligned_malloc` at RVA `0x005d5712` twice — once for the
container (size=0x3c, alignment=0x10) and once for the backing buffer
(size=arg1, alignment=arg2). Both calls are `__cdecl` (caller-cleans via the
single `ADD ESP,0x10` after the second call cleans all four pushed args).

The fact that the backing alloc happens **unconditionally** (even when the
container alloc returned NULL) means a follow-up matcher should look for a
companion **destructor / dealloc** sibling that mirrors this asymmetry — most
likely calling `_aligned_free` on the backing buffer first, then on the
container.

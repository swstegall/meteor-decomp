# engine_memory bookkeeping allocator — per-bucket counter tables

Discovered while matching `FUN_0040d300` @ 0x0040d300 (479-B,
EH3-SEH, `__thiscall void *alloc(size_t, const char *kind)`).

## What this function is

The engine's main allocator-bookkeeping entry. Caller hands it the
requested `size` (DWORD on the stack) and a static `kind` string
(e.g. `"CDev.Engine.Lay.Common.DArray"` / `"CDev.Engine.Lay.Common.STL"`,
both `.rdata` pointers — see callers `FUN_00aa3cc0`, `FUN_00a8f920`,
`FUN_00a8f8c0`, `FUN_00aa4b30`, `FUN_00a77600`, `FUN_00d4e0` etc.).
The function dispatches to one of two concrete allocators and then
bumps four parallel sets of counters before returning the user
pointer:

1. **Size-class bucket** (`this+0xcc + bucket*0x18`) — for the small /
   medium fast path through `FUN_0040d280` + `FUN_0040a840`.
2. **Generic "Mem.Space" bucket** (`this+0xb8`) — for the slow path
   through `FUN_0040e110` against the named space resolved by
   `FUN_0040e230(PTR_DAT_012652f8, "CDev.Engine.Lay.Mem.Space")`.
3. **Global summary** (`this+0x7c..+0x8c`).
4. **Per-allocation-site bucket** (`*(int *)(this+0x360) + site*0x14`)
   keyed by a 16-bit site id returned from `FUN_0040a710(kind)`
   (a strncmp-style scan against `PTR_s___Not_Categorized___00f558c0`).

All four buckets share the same five-DWORD shape:

```
struct AllocBucket {        // 0x14 / 0x18 bytes depending on bucket kind
    uint32_t count;         // +0x00  alloc count
    uint32_t /*class_size or kind*/; // +0x04 (small-bucket only)
    uint32_t cur_max_count; // +0x08  high-water count this generation
    uint32_t total_bytes;   // +0x0c  running total bytes
    uint32_t peak_bytes;    // +0x10  high-water bytes (all-time)
};
```

The bookkeeping idiom is the same six-instruction block four times
inside this one function:

```
        add  [esi+0x00], 1          ; ++count
        add  [esi+0x0c], ebx        ; total += size
        mov  ecx, esi
        call FUN_0040da50           ; uint cur_water = high_water()
        mov  ecx, [esi+0x08]
        cmp  ecx, eax
        jbe  +2
        mov  eax, ecx               ; eax = max(cur_water, cur_max_count)
        mov  ecx, [esi+0x10]
        mov  [esi+0x08], eax        ; cur_max_count = eax
        mov  eax, [esi+0x0c]
        cmp  ecx, eax
        jbe  +2
        mov  eax, ecx               ; eax = max(total_bytes, peak_bytes)
        mov  [esi+0x10], eax        ; peak_bytes = eax
```

## Layout of the `this`-relative tables (allocator object)

Offsets exercised inside this 479-byte function:

| Offset      | Purpose                                                |
|-------------|--------------------------------------------------------|
| `+0x64`     | `CRITICAL_SECTION` — guards all bookkeeping            |
| `+0x7c`     | global alloc count (`count` slot of the global bucket) |
| `+0x84`     | global cur-water peak count                            |
| `+0x88`     | global total bytes                                     |
| `+0x8c`     | global peak bytes                                      |
| `+0xa4`     | small-path summary bucket (5 DWORDs from here)         |
| `+0xb8`     | big-path "Mem.Space" summary bucket (5 DWORDs)         |
| `+0xcc`     | start of the 22-entry size-class bucket table          |
|             |   each entry is 0x18 bytes (so `+0xcc + i*0x18`)       |
| `+0x2dc`    | medium-size-class hit-count table (one DWORD per       |
|             |   bucket, indexed by `((size>>4) + (size&0xf?1:0))`)   |
| `+0x35c`    | small-size hit count (size < 9)                        |
| `+0x360`    | pointer to the per-allocation-site bucket table        |
|             |   (each entry is 0x14 bytes, indexed by FUN_0040a710)  |

## Class-size table at `DAT_00f55988`

A 22-entry sorted `uint32_t[]` of bucket upper-bounds in `.rdata` at
`0x00f55988`. `FUN_0040d300` linear-scans it to find the smallest
bucket whose ceiling is `>= size`; the index becomes the `i` in
`this+0xcc + i*0x18` above (with `-1` reserved for "didn't fit any
bucket", though that branch is unreachable from the size <= 0x200
fast path that gates this code).

## Allocation-site name table at `0x00f558c0`

`FUN_0040a710` ("FindNameSite", called as `EAX=kind; CALL rel32`) does
a strncmp-style scan of the registered names at
`PTR_s___Not_Categorized___00f558c0` — a `char **` table indexed by a
1-byte counter capped at `DAT_01265300` (a runtime-grown count).
Returns the 16-bit site id (sign-extended through `0fbf c0` =
`movsx eax, ax`) of the matching name, or a negative value if the
table is empty. The pseudo-name `"__Not_Categorized__"` is the
fallback bucket if `kind == NULL` (FUN_0040a710's first action is
`if (in_EAX == NULL) in_EAX = &DAT_00f5533c;` — the literal
`"__Not_Categorized__"` string).

The non-standard `EAX=kind` calling-convention is a deliberate MSVC
2005 optimisation: `kind` happens to already be in EAX after the
preceding `mov eax, [esp+0x2c]` reload, and the callee doesn't need
the C calling convention because it's never called from anything
that wouldn't preserve EAX naturally.

## Cross-reference: `FUN_0040adc0` is the matching free path

The sister function `FUN_0040adc0` (Ghidra 293 B, `__thiscall void
free(this, payload, size)`) walks the same `DAT_00f55988` table,
locates the `this+0xcc + i*0x18` bucket, decrements the same five
fields, and calls `FUN_0040a710` to update the per-site counters
the same way. Treat `0xd300` and `0xadc0` as a paired alloc/free
matcher.

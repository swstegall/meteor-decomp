## Function synopsis

`Node_d280 *BucketPool_d280::FUN_0040d280(unsigned int param_1)` —
__thiscall, 120 bytes, callee cleans 1 stack arg (RET 0x4).

Scans a 22-entry sorted threshold table (`g_thresholds[0..21]` at
`0xf55988`) for the first bucket whose limit >= param_1. Walks the
linked list at `this->nodes[i]` for a node with `field_a` (word at
+0x0a) > 0; returns it if found. If not found, calls
`FUN_0040d060(limit)` to allocate a node, inserts it via
`FUN_0040ab90(node, i)`, and returns it.

## Structural mismatches (not fixable from source)

### 1. JC vs JL at offset 0x1f (outer loop counter check)

The original at `0x0000d29f` uses `72 ef` — **JC** (unsigned below /
carry flag) — for the `CMP ESI,0x16; JC loop_top` outer loop back-edge.

MSVC 2005 SP1 with `/O2` generates `7c` (**JL**, signed less) for every
variant tested:

| Source form                           | Generates |
|---------------------------------------|-----------|
| `unsigned int i = 0; i < 0x16u; i++` | JL (7c)   |
| `int i = 0; (unsigned)i < 22u; i++`  | JL (7c)   |
| `int i = 0; i < 22; i++`             | JL (7c)   |
| `unsigned i; if (i >= 22) break`      | JL (7c)   |

The adjacent function `FUN_0040d300` (which calls this one and has an
identical loop shape with `CMP EAX,0x16`) generates JC with EAX as the
counter. The mechanism that causes JC vs JL is unclear — it may be
register choice (ESI vs EAX), loop unrolling context, or a specific
source-level form not yet tried. Without resolving this, every
compilation is a structural mismatch from offset 0x1f onward.

### 2. Two separate return-0 blocks (orig) vs one merged block (ours)

The original has **two distinct** 7-byte return-0 sequences:

- `0x0000d2a1..0x0000d2a5`: loop-fallthrough path (`5e 33 c0 5b c2 04 00`)
- `0x0000d2ac..0x0000d2b0`: dead-branch path (`5e 33 c0 5b c2 04 00`)

MSVC merges these into a single shared block in every variation tried,
saving 7 bytes. The dead-branch is produced by `TEST ESI,ESI; JGE
0x0040d2b3` — `i` is a loop counter incremented from 0, so the signed
comparison is always true. MSVC recognises the dead code and folds the
never-taken path into a jump to the fallthrough return. Reproducing two
separate identical return-0 blocks requires MSVC to NOT fold them —
which would need the second return to be unreachable via a non-obvious
path. No source formulation found that prevents the merge.

### 3. JGE (forward) vs our JL (backward) at offset 0x29

The original `TEST ESI,ESI; JGE 0x0040d2b3` (jump over the dead return
block, forward by 7 bytes) becomes `TEST ESI,ESI; JL <merged_ret>` in
our compilation because MSVC generates the code in a different order:
when the two return-0 blocks are merged, the single return lives before
the post-threshold body, so the conditional jumps backward rather than
forward. Same root cause as issue #2 — the jump direction is a symptom
of the merged-block layout, not an independent issue.

### 4. Missing 6-byte LEA NOP alignment pad at inner loop

The original has `8d 9b 00 00 00 00` (LEA EBX,[EBX]) immediately before
the inner-loop top at `0x0000d2c0` — a 6-byte NOP used for alignment.
Our compilation does not emit this pad because the inner loop starts at
a different position within the function (different cumulative byte
count due to issues 2 and 3). Loop-alignment NOPs in MSVC 2005 are
position-dependent — the pad is inserted to align the target to a
16-byte boundary in the final linked binary, not in the object file,
so this difference cannot be fixed until all preceding bytes match
exactly.

### 5. Size: 107 bytes vs 120 required

The combined effect of issues 2, 3, and 4 is that our best compilation
produces 107 bytes — 13 bytes short. The 13 missing bytes break down as:
7 (second return-0 block) + 6 (inner-loop LEA alignment NOP) = 13.

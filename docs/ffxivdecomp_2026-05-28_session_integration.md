## Wire protocol

### Two-tier outbound layer

ffxivDecomp newly establishes that the outbound wire is **two-tier**:
RUDP2 **segment-level transport** opcodes (`0x01` ping/40B, `0x02`
handshake, `0x03` 560B large state push, `0x04` disconnect-ack, `0x06`
24B heartbeat, `0x0e`/`0x11` disconnect) sit **below** the **application**
opcodes (Zone 0x12d–0x135, Chat 0xc8/0xc9/0x02/0x12c, Lobby
0x03–0x06/0x0b/0x0f/0x1f5/0x1f6). 21 application outbound opcodes across
3 channels. Opcode spaces are **per-channel** — the same opcode value
means different things on Lobby vs Zone vs Chat. *(`finding_outbound_complete_lobby_zone_chat.md`, `finding_ipc_channel_framing.md`, `finding_net_event_loop.md`)*

The live socket layer is **plain Winsock** (`select()`-driven I/O loop
`FUN_00d514f0` over a Socket wrapper, vtable `0x01113340`; state 4 =
CONNECTED_TCP/recv, 5 = CONNECTED_UDP/recvfrom; on-recv callback at
Socket+0x38). RUDP2 segments are framed **above** this generic socket —
grounding meteor-decomp's RTTI-only "RUDP2" model in `wire-protocol.md`
against actual `recv`/`send`/`select` call sites. *(`finding_net_event_loop.md`)*

### Outbound Zone application opcodes 0x12d–0x135 — DIRECTION CORRECTION

The single highest-value wire correction: **0x12d/0x12e/0x12f/0x131/
0x133/0x135 are CLIENT→SERVER senders**, traced from the actual EXE send
functions. meteor-decomp's `config/ffxivgame.up_opcodes.json`
`rx_opcode_validation` block labels them `OP_RX_EVENT_START`/`EVENT_UPDATE`/
`DATA_REQUEST`/`ITEM_PACKAGE_REQUEST`/`GROUP_CREATED`/`ACHIEVEMENT_PROGRESS`
(verified present in-repo). **meteor-decomp's own
`docs/ffxivdecomp_opcode_binding_map.md` already labels all six as
`opcode_sender` (OUT)** — so the two derived configs disagree with each
other; `up_opcodes.json` carries the stale wiki-derived RX names. *(`finding_outbound_complete_lobby_zone_chat.md`, `finding_executeCommand_outbound_path_CLOSED_0x12d_checksummed.md`)*

- **0x12d** (200B tagged container) — player command **and** the
  multi-purpose notice/server-notify container. Two modes:
  *immediate* (command vtable[0x1c]==1 → `Command_immediate_sendVia_0x12d_checksummed_v1v2` @ 0x00897310, CRC32) vs *queued*
  (flushed per-tick). Also carries the SIMPLE noticeEvent variant:
  `callServerOnX` → `ServerNotify_send_via_0x12d_simple_128Bpayload`
  (@ 0x006e2fb0, **no CRC**). A discriminator byte at **+0x28** selects
  the variant server-side. **The integrity field is a uint32 standard
  CRC32 at +0x24** (poly 0xEDB88320 = `Sqex::Crypt::Crc32` @
  `FUN_00d3a380`) over the 128B payload at +0x49 — **not** the 32 bytes
  at +0x29 (those are command-specific hash/id). CRC is transport
  integrity, not anti-cheat. 8 commandName flags: commandRequest/
  commandJudgeMode/commandDefault/commandWeak/commandForced/commandContent/
  widgetCreate/macroRequest. *(`finding_command_checksum_is_standard_crc32.md`)*
- **0x12e** (104B) — generic 6-arg Lua→server RPC, the universal
  request half of the request/response async pattern. +0x10 = method
  selector = sign-extended **first byte of a ResumeChecker RTTI string**;
  +0x14 = param hash (`FUN_00d3aae0`); +0x18 = sub-selector; +0x19 = 64B
  param buffer. Backs CreateStaticActor/CreateClientItem/GetString. The
  inbound server response wakes the paired ResumeChecker by sequence-id.
- **0x12f** (56B string-path WorkSync write) — CharaBase + Director
  `_updateWork` ONLY, with predictive UpdateQueue.
- **0x131** (24B byte-toggle, `_sendByteToggle`) — sit/stand-style
  boolean signal. **NOT** a server→client EndEvent (see SEQ-005 §).
- **0x132** (24B byte+ushort) — Item `_updateWork` ONLY, **no** WorkPath,
  no predictive enqueue. Carries item Bazaar/Trade lifecycle.
- **0x133** (56B, byte-identical to 0x12f) — GroupBase `_updateWork`
  ONLY, skips the predictive UpdateQueue (group state is
  server-authoritative). The 0x12f/0x133 split is a **server-side routing
  hint** (actor-table vs group-table); one parser can serve both.
- **0x134** (40B + 15-char nonce) — anti-tamper challenge.
- **0x135** (24B, uint32 bindingId at +0x18) — subscribe/query a
  binding-id. **WorkSync is SUBSCRIBE-based, not broadcast-all**: client
  sends the binding-ids it wants; server pushes only subscribed bindings
  (~10× bandwidth saving). 0x3f2/0x3f3/0x3f4 (=1010/1011/1012 = hp[1]/
  hpMax[1]/state_mainSkillLevel) always force the server query.

The asymmetric WorkSync wire model: C→S uses **verbose string WorkPaths**
over 0x12f/0x133 (rare player-UI events); S→C broadcast uses **compact
binding-ids** (frequent per-tick HP/MP/pos). The exact S→C compact-binding-id
opcode is **still unpinned** by ffxivDecomp (candidates 0x130/0x131
adjacent to 0x12f). *(`finding_worksync_inbound_wire_to_record_bridge_FULL_CHAIN.md`)*

### Lobby & Chat outbound (semantics behind already-imported names)

Lobby state machine `0→4→0xd→0xe→0xf→0x10`. Version constants the server
must accept: Zone+Chat handshake `0x3C6B` (15467) at body +0x00 of
session 0x02; Lobby `clientVer1=0x6e` (110) at +0x0a and `clientVer2=0x1347`
(4935) at +0x0c of 0x05/0x06. Chat outbound is **data-driven** (single
`ChatClient_dispatchOutbound_generic` @ 0x00db3e30 reads opcode+size from
a descriptor at +0x00/+0x04), unlike Zone/Lobby which hardcode one sender
per opcode; chat enforces handshake-first via state at this+0x8c. The 4
chat channels (32 notify / 33 alert / 38 NPC dialog / 40 say) all
multiplex into OUT opcode **0xc9** with the channel as a body
discriminator at +0x14; /tell needs the extra recipient slot → **0xc8**.
*(`finding_lobby_flow.md`, `finding_zone_chat_channel_architecture.md`, `finding_chat_block_command_notifications.md`)*

### Inbound dispatch — TWO tables

ffxivDecomp pins a **primary wire dispatcher** `FUN_004dc690`
(Zone_MAIN_inbound) that switches on the real 16-bit wire opcode at
`packet[+2]` across **0x143–0x1a8** (+ session 0x02–0x11, 0xca/0xcb).
The `0x00fdfb80` ~224-entry table that meteor-decomp's
`ffxivdecomp_inbound_opcodes.md` documents is a **separate downstream
CommandUpdater per-event sub-table** indexed 0–60 — those indices are
**NOT** wire opcodes a server picks. A server's actual wire opcodes are
the 0x143–0x1a8 family routed by `FUN_004dc690`. *(`finding_spawn_wire_side_CLOSED_opcode_0x17c_zone_main_inbound_dispatcher.md`, `finding_zone_inbound_game_opcodes_0x143_0x1a8_bridge_pattern.md`)*

Wire→subsystem routing map on the dispatcher object: this+0x08 spawn
pipeline; this+0x0c TEXT/LABEL mgr (0x198); this+0x18 generic-state
(0x143 despawn/0x186/0x187); this+0x24 actor-bound (0x146/0x148–0x156/
0x176/0x18f/0x190/0x191); this+0x10c UI/message-pool (0x193/0x196/0x1a3);
this+0x4d8 session-bound (0x18d); this+0x4e0 default fallback. Inbound
sequence threshold **0x1c11** (`FUN_004e5ff0`): packets with seq < 0x1c11
are red-black-tree inserted for in-order delivery; ≥ 0x1c11 discarded
(sliding-window reassembly). *(`finding_misc_game_opcodes_0x186_0x18a_0x191_0x196_0x198_characterized.md`)*

### Spawn / actor lifecycle (0x17c / 0x143)

Actor spawn is opcode **0x17c** (Group::EntryBuilder typed packet, ~120B,
class-name string at +0x44, TYPE_TAG at +0x10: 0=EntryBuilder /
0xe=OnlineStatusUpdater); despawn is **0x143** (Group::BreakupBuilder,
~32B id-only). Both share **one ring buffer** and the 6-stage per-frame
drain (T0–T5, max 2 entries/tick → the visible gradual zone fade-in). T5
allocates an 84B actor + ctor `FUN_006c83d0` + `actor:_onInit` + a 0x133
worksync-init ACK. The spawn ACK protocol: client replies **2× 0x130**
(listObjectQueueAdd + Delete, 32B each, payload = the resolver_id+
primary_id the server sent) + **1× 0x133** init ACK. *(`finding_spawn_pipeline_typed_packet_ring_buffer_6_stage_architecture.md`, `finding_opcode_0x143_DESPAWN_packet_breakupBuilder_path.md`)*

**The Group::PacketRequestBase hierarchy meteor-decomp analyzed as the
party/group system (Phase 8, `group_system_decomp.md`) IS ALSO the actor
spawn/despawn pipeline.** EntryBuilder=add, BreakupBuilder=remove,
OnlineStatusUpdater/MemberInfoUpdater/PropertyUpdater/WorkSyncUpdater=
state replication. It is a general typed-object replication system, not
party-specific. Independent vtable confirmation: PacketRequestBase
vftable VA 0x00fd4120 (13 slots) == meteor-decomp's RVA 0xbd4120.

### Per-actor 3×5 message matrix (0x148–0x156)

15 opcodes = **3 payload types × 5 size variants**, no per-packet header
(opcode encodes type+size; server picks the smallest that fits N):

- **TYPE A** (0x148–0x14c) = ACTION RESULTS, 112B/record (source/target
  ids, value fields, ushort animation id @ +0x14, 4 target refs @ +0x18,
  optional 64B status-chain ext @ +0x44 gated by flag @ +0x29).
- **TYPE B** (0x14d–0x151) = STATUS EFFECT entries, 6B (ushort status_id +
  ushort dur/value + byte flag); 0x14f = 16-slot list (matches the 1.x
  16-status-icon UI limit), 0x150 = 32 extended.
- **TYPE C** (0x152–0x156) = ID LISTS, bare 2B ushorts.

Variants per type: SINGLE / VARIABLE(count byte, @ +0x380 for 0x149) /
FIXED-16 / -32 / -64. Two-layer dispatch: outer `FUN_00576560`
(actor-lookup) → inner per-actor-queue sub-dispatcher (`FUN_00580e70`…,
+0x80 stride, RB-tree at this+0x10). Type A 112B layout is directly usable
for garlemald combat-result builders. *(`finding_per_actor_message_3x5_matrix.md`)*

## Structural intel for matching

### Master scheduling skeleton

`Application_mainTick` (`FUN_004da680`) → `PerFrameTick` (`FUN_00578970`)
dispatching **15 fixed subsystem slots**: slot[6]=spawn pipeline (2/frame),
slot[7]/[8]=inbound WorkSync pump (32 items/tick each), slot[10]=timeout
monitor (900-frame/15s @ `FUN_00770c00`), slot[12]=dead-session GC, slot

0x7a122/0x7a123 + mode root 0xc0000024). This is the matching anchor for
every per-tick consumer scattered across meteor-decomp's docs. *(`finding_perFrameTick_subsystems_COMPLETE_15_slots_characterized.md`)*

### Spawn / class-system thunks

`_createActor` (thunk `FUN_00709640`) dispatches polymorphically through
**vtable[0x6c] (slot 27)** = the per-class spawn ctor wired by
`_defineClass` — the mechanical answer to "which Lua-class wrapper does
AddActor construct." Returns a 16-byte `OnInitResumeChecker` the script
yields on. `_canCreateActorByName` (`FUN_006ff1a0`): a class is
NON-creatable iff its category tag is one of 3 sentinels (`DAT_0130d4fc`/
`d500`/`d504` = abstract-root / singleton WorldMaster / engine-spawned
Director) — tells the server which classes are NOT spawnable by wire
opcode. Class-system thunk family: `_defineClass`/`_createActor`/
`_isInstanceOf`/`_canCreateActorByName`. *(`finding_lua_class_system_3_thunks.md`)*

### ResumeChecker — universal yield (~24 subclasses, was 11)

Every Lua "wait/async return" allocates a concrete ResumeChecker subclass
(3-slot vtable, `isReady()` is the fixed slot); pushed via
`CoroutineContext_pushResumeChecker`; a per-tick pump walks pending
checkers and resumes on `isReady()==true`. **No other yield path exists in
1.x Lua.** RPC-backed checkers pair with a 0x12e selector byte. The +13
newly enumerated via RTTI include `ClientOrderEventWaitingResumeChecker`,
`s_FadeResumeChecker`, `s_MapLoadResumeChecker`, `CutScenePlayingResumeChecker`,
`WaitLoadFormResumeChecker`, `s_PreloadResumeChecker`, `CancelResumeChecker`
— all confirmed present in meteor-decomp's `legacy_structs.json`/`rtti.json`.
A **second** async interface, `FunctionEndCallbackInterface`, runs a 2-tier
pattern (40B FunctionEndCallback for disk-I/O completion → 148B
LoadDataResumeChecker the script yields on; dual CoroutineContext queues +
`findPendingCallback` dedup) — relevant to Phase 4 Pack/ChunkRead. *(`finding_resumechecker_full_inventory_10_subclasses_confirmed.md`, `finding_outbound_rpc_0x12e_format_plus_resumechecker_count_correction.md`)*

### Lua base classes & dispatch paradigms

**Five** distinct C++↔Lua call paths (not 2): P1 `invokeLua`
(`FUN_00cc7a90`, ~80 `_on*` callbacks); P2 `registerLua` (123 Functor

## Corrections / corroborations vs meteor-decomp's existing docs

### Corrections (verified in-repo)

1. **0x12d/0x12e/0x12f/0x131/0x133/0x135 direction.**
   `config/ffxivgame.up_opcodes.json` `rx_opcode_validation` labels these
   `OP_RX_*` (inbound). They are CLIENT→SERVER senders.
   `docs/ffxivdecomp_opcode_binding_map.md` already labels them
   `opcode_sender` — the two configs contradict each other; the RX names
   are wiki-derived and wrong.
2. **Chat inbound entries 36/37 swapped.**
   `docs/ffxivdecomp_inbound_opcodes.md` lines 97–98 carry the **stale
   pre-correction** labels (36 = "40-char name", 37 = "/tell-style").
   ffxivDecomp's decompiled-and-corrected
   `finding_inbound_chat_handlers_3_variants_decompiled.md` puts **/tell
   at entry 36** (sender@+9, recipient@+0x29, body@+0x49, ~137B) and entry
   37 as the simple variant (sender + flag + lang, no recipient). Entry 41
   is NOT chat (request/response result push).
3. **0x131 ≠ server→client EndEvent.** ffxivDecomp's OUT 0x131 is a 24B
   `_sendByteToggle`. meteor-decomp's `seq005_kick_gate_analysis.md`
   `0x0131` is **garlemald's own server-side opcode constant** for
   EndClientOrderEvent — a *different opcode space*. No code-side conflict,
   but the doc should disambiguate so task #24 targets the right wire op.
4. **`_updateWork` is per-class, not uniform.** CharaBase/Director=0x12f,
   Item=0x132 (no WorkPath), GroupBase=0x133 (per-instance dispatch at
   instance+0x68). Matching must not assume uniform `_updateWork` thunks.
5. **0x12d checksum is at +0x24 (CRC32), not the 32 bytes at +0x29.**
6. **WorkSync is subscribe-based, not full-broadcast.**
7. **0x143 is DESPAWN**, not a generic state event — retire any prose that
   groups it with subsystem_0x18 generic state.
8. **Job-ID map** (server data, from Soul Crystal item ids 2000201–7):
   15=MNK, 16=PLD, 17=WAR, 18=BRD, 19=DRG, 26=BLM, 27=WHM.
9. **Gear-variant tables** (~625 class/job families) are 100% localized
   TEXT — gear stats live only in 5 sheets (itemData/equipment/weapon/
   armor/accessory). A server needs ~45 data tables, not 164+625.
